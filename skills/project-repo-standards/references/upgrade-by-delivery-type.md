# 按交付形态定升级策略

Web 服务、桌面客户端、安卓 App、嵌入式固件、浏览器扩展，这五类的「升级」是完全不同的问题。把它们混在一起谈，必然写出既不适合固件也不适合 Web 的废话。

**先问一句：这个交付物的代码跑在谁的机器上、谁能决定它什么时候更新？** 答案决定一切。

## 0. 一张表看清差异

| 形态 | 代码跑在哪 | 版本由谁持有 | 更新时机谁决定 | 升不上去的后果 |
|---|---|---|---|---|
| Web 服务 | 你的服务器 | 服务端 | 你（部署即生效） | 用户立刻不可用，可秒回滚 |
| 桌面客户端 | 用户电脑 | 用户机器 | 用户 / 自动检查 | 用户可以继续用旧版，长期分裂 |
| 安卓 App | 用户设备 | 用户设备 | 用户 / 应用内检查 / 商店 | 旧版本永久存在，接口不能随意下线 |
| 嵌入式固件 | 设备板子上 | 设备本身 | OTA 或人工烧录 | **最严重**：可能要拆机、上门、召回 |
| 浏览器扩展 | 用户浏览器 | 浏览器 | 商店审核 / 更新 URL | 旧版本存在，但可服务端禁用旧版 API |

一句话原则：**代码离你越远，升级机制越要在写第一行业务代码之前就设计好。** Web 可以事后补，固件不行。

## 1. Web 服务：不需要「客户端升级」，但必须设计「回滚」

Web 的"升级"其实是部署，用户永远拿最新版，所以不需要版本协商、不需要强制升级弹窗、不需要安装包。真正要设计的是**升级失败怎么退**：

- **镜像/制品要有唯一 tag**，禁止只用 `latest`（否则回滚时不知道退到哪个）。
- **回滚点在发布前创建**：旧镜像打 rollback tag、GitOps manifest 留旧 commit。
- **数据库迁移必须向前兼容**：先加列（可空）→ 双写 → 回填 → 再删旧列。禁止单次破坏性改表，否则代码回滚了数据库回不去。
- **前端静态资源带内容 hash**，`index.html` 不缓存，否则用户拿到新旧混合的产物。
- **健康检查要看业务**，不只看进程活着（`/health` 返回 200 但数据库连不上是常见假活）。
- **灰度优先**：canary 一小部分流量，观察错误率再全量。

不需要的东西（别过度设计）：客户端版本号上报、强制升级、安装包签名。

## 2. 桌面客户端：必须自带「版本清单 + 自动更新」

桌面客户端装在用户机器上，你不部署就等于没修 bug。最小机制：

| 必需件 | 作用 | 不做会怎样 |
|---|---|---|
| `latest.json` / `manifest.json` 版本清单 | 客户端读它判断有没有新版 | 用户永远停在旧版 |
| 安装包 + 校验和（sha256） | 下载完整性与防篡改 | 下到半截包，装完打不开 |
| 代码签名 | 系统信任（Windows SmartScreen / macOS 公证） | 弹"未知发布者"，用户不敢装 |
| 自动更新器 | 检查、下载、替换、重启 | 每次手动发链接，没人升 |
| 回滚/保留旧版 | 新版本崩溃时能退 | 新版本一挂，用户彻底用不了 |

经验点：

- **发版流水线产物必须与 GitHub Release 附件一致**，别让客户端从两个地方拿包。
- **国内下载走 Gitee 镜像**（GitHub Release 在国内经常龟速/超时），但版本清单仍以 GitHub 为准，避免两边版本不一致。
- **升级失败要能静默重试**，不要弹一堆错误框；用户只关心"能不能用"。
- 增量更新（差分包）能省带宽，但**必须能回退到全量包**——差分包做错会让客户端变砖。

## 3. 安卓 App：签名是一辈子的承诺

安卓特有的两个硬约束，任何一个搞错都是灾难级：

### 3.1 签名密钥永不更换

- 同一个 `applicationId` 的更新包，**签名必须与已安装版本一致**，否则系统拒绝覆盖安装，用户必须卸载重装（数据全丢）。
- 密钥丢失 = 这个包名永远无法再发更新，只能换包名重新开始（等于丢掉所有用户）。
- 因此：**密钥不入仓库明文**（base64 存 CI secret），但**必须有多处离线备份**，并且把签名指纹写死在 CI 里做闸门校验。

CI 里应该有的闸门（缺一不可）：

1. `apksigner verify --print-certs` 的 SHA-256 == 代码里写死的指纹。
2. `aapt dump badging` 的 `versionName`/`versionCode` == 本次 tag 的版本。
3. **`versionCode` 严格递增**（与更新通道里已发布的元数据比较）——不递增的话客户端根本看不到更新，这是最隐蔽的错版。
4. 产物 sha256 == 服务端回报的 sha256（发布后自验）。

### 3.2 版本号双轨制

- `versionName`（给人看，`1.4.2`）可以随便跳；
- `versionCode`（给系统看）**只能单调递增**，且一旦发布就永久占用，不能复用。
- 两者必须与 git tag 对齐，**在 CI 里自动对账**，不要靠人记得改。

### 3.3 升级策略要显式

- **强制升级**：接口不兼容/安全漏洞时用，但要给用户明确提示和下载入口，不能静默失效。
- **可选升级**：常规功能更新，不阻断使用。
- **灰度**：按设备/渠道分批放量，别一次全推。
- **设备形态分流**：一个包同时服务 TV 与手机时（按 `uiMode`/触屏/leanback 判断），共用一份版本节奏——这是可接受的简化，但要写清"两个形态一起发"。

### 3.4 服务端要能回答三个问题

1. 这台设备现在跑的是哪个版本？（设备上报，落库）
2. 它该升到哪个版本？（服务端返回，不是客户端猜）
3. 升级失败了没有？（下次心跳带上失败原因）

答不出这三个问题，就没有灰度、没有统计、没有故障定位能力。

## 4. 嵌入式固件：唯一「升不上去就要上门」的形态

固件的约束比 App 严一个量级：**断电是常态、设备可能失联、没有屏幕、没有用户交互、拆机成本极高**。

### 4.1 必备机制（缺一不可）

| 机制 | 为什么必需 |
|---|---|
| **A/B 双分区或 bootloader 双 bank** | 写入过程断电不能变砖；新固件启动失败要能自动回滚到旧版 |
| **固件包签名 + 校验和** | 防止半包、错包、被篡改的包被刷进去 |
| **版本号可读取并上报** | 现场设备跑什么版本必须可见，否则无法判断升级是否生效 |
| **允许降级** | 新固件有致命 bug 时，要能退回旧版（很多实现默认禁止降级，出事时无解） |
| **升级状态机 + 超时** | 下载中/校验中/写入中/待重启，每步都要有超时和重试，且状态要能查询 |
| **看门狗** | 新固件卡死时能自动复位并回滚 |

### 4.2 经验点

- **不要在升级过程中擦除 bootloader 区**，只写应用区。
- **升级包要包含完整镜像**（除非有把握做差分），差分升级在固件上出错代价太高。
- **OTA 服务端要能按设备型号/硬件版本下发不同固件**，硬件改版后固件不兼容是常见事故。
- **首次烧录与 OTA 走同一套镜像格式**，避免"产线能刷、OTA 刷不了"。
- **升级窗口要避开业务时段**（比如采数设备别在采集时升级）。
- **保留一个"恢复模式"**（按键/串口/USB），OTA 彻底失败时至少能本地刷。

### 4.3 CI 该做什么

- 编译产物必须带版本号与构建 hash，并能追溯到具体 commit。
- 产物大小、分区占用要有检查（超 flash 容量直接失败）。
- **固件 bin 要归档保存**（每版都留，因为现场回滚需要旧版 bin）。

## 5. 浏览器扩展：跟着商店节奏走

- `manifest.json` 的 `version` 是唯一版本源，商店据此判断更新。
- 自建分发的扩展需要 `update_url` 指向一个 XML/JSON 清单。
- 权限变更会触发用户重新授权（甚至被商店下架），加权限要当作破坏性变更对待。
- 旧版本会长期存在，服务端接口要向后兼容至少一个大版本。

## 6. 共同的元原则

1. **版本号只有一个真源**（git tag），其余地方（代码里的常量、产物元数据、更新清单）都必须与它对账，且由 CI 校验，不靠人。
2. **每个已发布版本都要能重新构建出来**（tag + 锁文件 + 固定构建环境）。
3. **发布前先想回滚**：回滚路径不通，就不要发。
4. **升级能力要在第一个版本就上线**，别等有用户了再补——固件和 App 尤其如此，第一版没做升级通道，后面每台设备都要人工处理。
5. **能观测才算完成**：发布后必须能看到"有多少设备升到了新版本"，否则等于蒙眼发版。
