# 故障对照表

| 现象 | 含义 | 处置 |
|---|---|---|
| `File is not a zip file` | 用了 REST 上传口发单文件 HTML | 单文件改走 MCP 的 `html` 参数，或把文件打成 zip |
| 返回链接 404 | 打包入口解析回落（zip 带顶层目录） | 传 `X-Entry-File: demo/index.html` 指定真实入口；发布后必 curl 一次断言 200 |
| 用户点开是 `127.0.0.1` / `localhost` | 链接没改写 | 换成 `http://100.64.0.88:8088/...` 再发；或用响应里的 `abs_url` |
| 手机打不开链接 | 手机没连内网（局域网 / ZeroTier / VPN） | 让手机先打开 `http://100.64.0.88:8088/api/health` 自检；本服务没有公网入口 |
| 工具列表里没有 static-deploy | 客户端没配上端点 | 按 `config-snippet.md` 加配置后重启客户端；探针：`POST /mcp` 发 initialize（`GET /mcp` 返 405 是协议要求，不是故障） |
| 返回 413 / Payload Too Large | 上传超过服务端上限 | 见下「大文件怎么处理」；按提示压缩或拆分 |
| 上传成功但页面白屏 | 入口错 / 资源引用是绝对路径 | 用相对路径引用资源，确认 `X-Entry-File` 指向真实入口文件 |
| 中文项目名显示成乱码 | 客户端把 header 二次编码了 | 直接传 UTF-8 原文即可（服务端原文与 URL 编码两种形式都认）；若仍乱码，检查中间是否有反向代理改写 header |
| `内容总量超过 20MB` | MCP 参数塞了太多内容 | 改用 HTTP 直传 zip，见 `publish-patterns.md` |

## 大文件怎么处理

单次上限 100 MB（zip 或图片原始字节）。接近或超过时的顺序：

1. **压缩**：图片转 WebP（通常省 60~80%）、HTML 去掉无用资源、字体只留用到的字形子集
2. **剔除**：`node_modules`、`.git`、`*.psd`、原始设计稿、超清原图都不要发
3. **拆分**：拆成多个子项目分别发布，用绝对链接互跳
4. **视频/超大资源不走这个服务**：它面向原型预览，不是文件分发；大文件用别的通道传，原型里引用绝对地址

服务端有解压防护（解压后总量、单文件大小、文件数量都有上限），超了会明确拒绝并清理半成品目录——那是保护机制，不是故障。

## 发布后自检（推荐养成习惯）

```bash
# 拿到响应后，先自己开一次链接确认 200，再发给用户
curl -s -o /dev/null -w "%{http_code}\n" "<abs_url>"
```
