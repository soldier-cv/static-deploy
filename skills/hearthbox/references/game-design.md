# 设计一款 Hearthbox 游戏

这不是"怎么写代码"（那是 `references/game-dev.md`），也不替代通用的游戏理论。

## 开工前先加载这三个技能

| 技能 | 什么时候必须加载 |
|---|---|
| `game-design` | 定核心循环、数值平衡、玩家心理、进度曲线 |
| `2d-games` | 涉及 2D 渲染、碰撞、tilemap、相机 |
| `game-art` | 定视觉风格、色板、素材管线 |

**这三个是硬要求。** 本文件只讲"先做什么后做什么"，不讲"游戏该怎么做"。
漏掉它们，产出会是"代码能跑但玩法空洞"——这是最常见的失误。

需要音频时加 `game-audio`。不确定用哪套时先用 `game-development`，
它是编排技能，会路由到对应的子技能。

这个文件解决的是**流程**：什么先定、什么后做、每步产出什么、什么时候算真的完成。
目标是**少返工**。

## 为什么流程比技术更容易翻车

一条实测数据值得先记住：同一个项目用 30 份设计文档 vs 只 1 页 brief，两版都做出了能跑的游戏，但盲评把 30 份那份排最后。**多出来的 29 份买到的是可追溯性，不是更好的游戏。**

但另一头是真的：**卡带格式、受限 API、美术规范这三样没定就开工，第二阶段重构时已产出的每款游戏都会报废。**

所以流程的核心不是"多写文档"，而是**把会返工的东西前置**。下面 5 步，每步只产出一样东西。

## 第 0 步：先判断现状（不要猜）

问清三件事之一：

| 用户状态 | 你要做的 |
|---|---|
| "我有个想法" | 从第 1 步开始 |
| "我要做成像 XX 那样" | 先问「哪个动词是你真正想要的」，再进第 1 步 |
| "已经有代码了" | 跳到第 4 步，先补美术规范 |

## 第 1 步：玩法一页纸（唯一核心动词）

**产出：一段话 + 一张 8 行的表。**

核心动词只能有一个。填不出来的话，说明玩法还没想清楚，别往下走。

```
一句话：玩家在 ____ 里 ____，以 ____。
核心动词：____（跳跃 / 射击 / 堆叠 / 连接 / 躲避 —— 只能选一个）
失败条件：____
成功条件：____
一局时长：____ 分钟
操作数：____（方向键之外还需要几个键）
```

判断标准：**读完后一个没玩过的人能说出"第一分钟我在干什么"。**

做完立刻验一次：这个动词能不能只用 `ctx.input.p1` 实现？如果需要鼠标、需要两套输入，说明操作复杂度已经超出"小游戏"范围了。

## 第 2 步：定美术规范（必须最先定，且写死）

**产出：一份 5 行的规格表，写进游戏仓库的 `docs/art.md`。**

AI 生成素材的默认行为是每次独立生成。不约束时必然出现：色盘漂移、描边风格不一致、sprite 尺寸不齐。最终游戏能跑，但看起来像素材拼贴。

| 项 | 要写死的内容 | 示例 |
|---|---|---|
| 逻辑分辨率 | 与 `game.json` 一致 | `320×180` |
| 色板 | **列出全部 hex**，不许越界 | 见下 |
| sprite 网格 | 所有素材对齐的基准尺寸 | `16×16` |
| 描边/光照 | 统一风格 | `1px #1a1a24 描边，左上光源` |
| 命名规则 | 便于程序查找 | `spr_hero_idle_0` |

色板要真的列出来，不是写"16 色像素风"：

```
#0b0b0f  #1a1a24  #2a2a36  #43435a
#6a6a7a  #9a9aa8  #d0d0d8  #f2f2f5
#f5a524  #ff6b35  #4ade80  #2dd4bf
#60a5fa  #818cf8  #f472b6  #c084fc
```

**建议先跑一个 16 色方案。** 色数越少，AI 出图一致率越高，程序也越好写（调色板索引比 hex 好管理）。

分辨率怎么选：像素风 320×180（1080p 恰好 6 倍整数放大，不出毛刺）。矢量风可以用 `720×405` + `scale: "fit"`。**定完不要改**，改了所有素材重画。

## 第 3 步：系统表（能填数才算想清楚）

**产出：一张表，每行都必须能填进具体数字。**

填不出的行就是没想清楚，不要用"-"糊过去。

| 系统 | 要定的 | 例子 |
|---|---|---|
| 数值 | 血量、速度、伤害、冷却 | `速度 90 px/s`、`跳跃初速 320` |
| 成长 | 有没有升级、曲线 | `每 5 关 +1 心` |
| 物品 | 种类、效果、出现率 | `加速 15%、持续 8s、出现率 12%` |
| 经济 | 有没有货币、怎么花 | 无（小游戏可以没有） |

**没有 magic number 散落在代码里。** 所有数值集中在 `src/config.ts` 一个文件，改数值不改逻辑。

## 第 4 步：垂直切片（一次只打通一条链路）

**产出：一个能在 10 分钟内玩完、有开头有结尾的原型。**

这一条最容易做错。**不要"先写完所有系统再联调"**，而要"一次只打通一条从输入到反馈的完整链路"。

第一版应该长这样（按顺序，每完成一条能玩就停下来验）：

1. 画布能出画面，方块能动 ← 输入链路
2. 玩家能撞到东西并被挡住 ← 碰撞链路
3. 撞到会掉血、掉完会死 ← 状态链路
4. 死掉能重开、进度能存 ← 存档链路
5. 有开始画面、有结束画面 ← 闭环

**每一轮都必须能玩。** 能编译的空壳不算完成。

用 `ctx.random` 而不是 `Math.random()`，这样 `?debug=1&seed=42` 能复现整局。

## 第 5 步：验收（截图存证，不可豁免）

**改到玩家可见的东西，必须真跑起来并截图。`typecheck` 通过不算跑通。**

菜单画到屏幕外、字体缺字形、手柄映射反了——这些代码层面全部"正确"，只有跑起来才看得见。

验收清单：

```
[ ] pnpm dev 起来了，游戏出现在货架上
[ ] 点进去能玩，不是黑屏
[ ] 键盘能玩（方向键 + 动作键）
[ ] 鼠标操作准确（如果游戏用鼠标）
[ ] 死亡后能重开
[ ] 刷新页面后存档还在
[ ] 截图存到 evidence/
```

截图怎么拿：用 `playwright-skill` 或 `webapp-testing`，或者直接 `page.screenshot()`。**没有截图的"完成"都是假的。**

## 什么时候用哪个技能

| 你要做的事 | 用哪个 |
|---|---|
| 定流程、玩法、美术规范、验收 | **本技能** |
| 具体写代码、接 API、排查黑屏 | `hearthbox-game` |
| sprite 组织、tilemap、物理、相机 | `game-development` 的 `2d-games` |
| 数值平衡、玩家心理、进度曲线 | `game-development` 的 `game-design` |
| 改平台本身 | `hearthbox-platform` |

**它们不冲突**：`2d-games` 告诉你"碰撞检测用 AABB"，本技能告诉你"先做碰撞链路再做敌人"。

## 反模式（中了就停手）

1. **先写 30 份文档**：盲评垫底。4 份够了（玩法一页纸、系统表、设定圣经、美术规范）。
2. **美术规范最后定**：所有素材要重画。必须最先定。
3. **一次性让 AI 生成整个游戏**：必然得到能编译、不能玩的东西。
4. **数值散落在代码里**：改一个数要翻五个文件。
5. **只看 typecheck 通过就交付**：没有截图证据的完成是假的。
6. **第一版就想做完整内容量**：先做 10 分钟能玩完的。

## 一份最小产出物长什么样

游戏仓库里最终应该有这四份（不是三十份）：

```
my-game/
├── docs/
│   ├── pitch.md      # 玩法一页纸：核心动词 + 八个字段
│   ├── systems.md    # 系统表：数值/成长/物品/经济，全是数字
│   ├── art.md        # 美术规范：分辨率/色板/网格/描边/命名
│   └── world.md      # 设定圣经：角色/世界观（可以边做边长）
├── evidence/         # 验收截图
└── src/config.ts     # 所有数值集中在这里
```
